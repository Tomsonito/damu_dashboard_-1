# Развёртывание на сервере (этап 5)

Шаблоны и порядок действий для выката дашборда на боевой сервер. Все файлы
здесь — **заготовки с плейсхолдерами** `<...>`: подставьте свои значения на
месте. В git они лежат осознанно (это не секреты); секреты — только в `.env`,
который в `.gitignore`.

Готовить начали 24.07.2026, ещё **без доступа к серверу** — чтобы к моменту
доступа осталось подставить пути и проверить, а не писать с нуля.

## Что уже сделано в коде (не требовало сервера)

- **Версии зависимостей зафиксированы** (`requirements.txt`, через `pip freeze`) —
  сервер поднимется с теми же версиями, что проверены локально.
- **`pip-audit` чист** — известных уязвимостей в зависимостях нет (24.07.2026).
- **Отладчик выключен по умолчанию** — `debug` в `app.py` включается только
  переменной `DASHBOARD_DEBUG=1`; на сервере её не задаём.
- **Кэш переведён на `FileSystemCache`** (`core/cache.py`) — воркеры Gunicorn
  делят один кэш на диске, а не греют каждый свой в памяти.
- **DuckDB проверен под параллельной записью** — см. «Известное ограничение».

## Порядок выката

1. **Доступ и запуск вручную** (задача 30 в ROADMAP)
   ```bash
   ssh <сервер>
   git clone <репозиторий> && cd damu_dashboard
   python3 -m venv .venv && . .venv/bin/activate
   pip install -r requirements.txt
   cp .env.example .env    # затем вписать строку подключения к боевой БД
   python -m etl.run       # первая загрузка (публикуется сразу)
   python app.py           # проверка: curl http://127.0.0.1:8050 отвечает
   ```

2. **Gunicorn + systemd** → [`damu-dashboard.service`](damu-dashboard.service)

3. **Nginx (HTTPS, rate limit)** → [`nginx-damu-dashboard.conf`](nginx-damu-dashboard.conf)

4. **cron на ETL** → [`crontab-damu.txt`](crontab-damu.txt)

5. **LDAP/AD-вход** — заменить заглушку `core/auth.py` реальным входом.
   **Писать по факту, когда будут реквизиты домена** (адрес контроллера,
   base DN, группы для роли admin) — заранее это гадание. Сейчас `auth.py`
   возвращает admin всем; пока LDAP нет, **сайт наружу не выкатывать**:
   форма ввода плана открыта каждому.

6. **Бэкап** `data/analytics.duckdb` — единственные невосстановимые данные
   там таблица `plan` (ручной ввод, в боевой БД её нет). Бэкапить **только
   `.duckdb`**, папку `data/cache/` — не нужно (восстановимый мусор).

7. **Чек-лист безопасности** (лист «Безопасность» в Excel-плане, 12 пунктов),
   включая проверку, что сайт недоступен из интернета мимо VPN.

## Известное ограничение: DuckDB и несколько воркеров

DuckDB — встраиваемая БД по модели «один писатель ИЛИ много читателей».
Под Gunicorn несколько процессов-воркеров плюс cron обращаются к одному
файлу. Проверено стресс-тестом (24.07.2026, 9 процессов, один файл):

- **Целостность гарантирована.** Конкурентная запись даёт честный отказ
  (`IOException`), а НЕ порчу файла: транзакции ACID держат, инвариант
  «ровно одна опубликованная версия» не ломается. Для финансовых данных
  это главное.
- **Под реальной нагрузкой отказов почти нет.** При реалистичном ритме
  (ETL раз в 5 мин, публикация раз в день, правки плана изредка, чтения
  частые) — 1 отказ на ~270 операций, и тот у ETL, который просто повторится
  через 5 минут. Запись в файл реально происходит единицы раз в день,
  конкурентных писателей практически не бывает.
- **Повторы с запасом.** Обращения к занятому файлу повторяются с
  экспоненциальным backoff и разбросом (`core/data.py`, `_lock_delay`) —
  окно ожидания ~4 сек, чего хватает поймать свободный момент.

**Когда это перестанет годиться:** если читателей станет в разы больше или
записи участятся (несколько правок плана в минуту), файловый single-writer
станет узким местом. Тогда — вынести витрину на клиент-серверную БД
(тот же PostgreSQL) или поставить очередь записи. Менять стоит по факту,
а не заранее: сейчас для ~70 читателей и редких записей DuckDB справляется.
