АУДИТ БЕЗОПАСНОСТИ, ПРОИЗВОДИТЕЛЬНОСТИ И АРХИТЕКТУРЫ
Проект: damu_dashboard
Дата аудита: 18.08.2026

ИТОГ

Проект уже крепкий для предбоевого MVP, но выпускать его в production пока
нельзя. Главные блокеры — отсутствующая аутентификация, обход ролевых проверок
через callback API, SQL из клиентских значений, демо-данные в боевой
конфигурации и многопроцессная запись в DuckDB.

Во время аудита исходники и конфигурация не изменялись.


ЧТО ПРОВЕРЕНО

- Структура, Python-код, Dash callbacks, ETL, DuckDB, кэш, конфигурация,
  Nginx, systemd и cron.
- Все 129 тестов: 126 прошли, 3 ожидаемо пропущены для разделов без данных.
- pip check: зависимости совместимы.
- Актуальный pip-audit: известных уязвимостей в 74 установленных пакетах
  не найдено. Это проверка известных уязвимостей, а не статический анализ кода.
- .env не отслеживается сейчас и не обнаружен в истории Git.
- Текущий снимок после подключения demo: 184 703 строки, около 15,7 МБ
  в памяти; load_facts() занимает медианно около 61 мс.
- Файловый кэш: 13 файлов, 22,84 МБ.


P0 — БЛОКИРУЕТ PRODUCTION

1. Реализовать настоящую аутентификацию до любого сетевого размещения.

   Сейчас core/auth.py всегда возвращает роль admin, а имя пользователя
   берётся через getpass. На сервере действия будут записываться от имени
   служебной учётки. Предпочтительно использовать корпоративный
   SSO/OIDC/Kerberos на reverse proxy или IdP. Прямой LDAP допустим только
   с LDAPS/StartTLS, проверкой сертификата и deny-by-default mapping групп.

2. Проверять роль внутри каждого изменяющего callback.

   Ограничение layout() защищает только интерфейс. Запрос к
   /_dash-update-component можно сформировать напрямую.

   - pages/plan_input.py: можно отменять планы, ставить и снимать вето.
   - pages/widgets_edit.py: можно менять состав экранов.
   - В pages/settings.py проверка внутри callback уже есть — это правильный
     образец.

   Нужен общий server-side guard/decorator и тесты:
   anonymous -> 401, viewer -> 403, admin -> успех.

3. Устранить SQL injection через клиентский page.

   Значение приходит из браузера и вставляется через f-string в
   core/widgets.py: is_customized(), get_widgets() и last_change().
   Открытие БД в read_only=True ограничивает порчу базы, но не исключает
   подмену результата и чтение доступных процессу данных.

   Рекомендации:

   - Все значения передавать параметрами ?.
   - page, section, tab, chart type и имена колонок проверять по закрытым
     allowlist из конфигурации.
   - Для web-соединения отключить внешний доступ DuckDB и загрузку расширений.
   - Аналогично защитить динамические идентификаторы в core/db.py и ETL.

4. Запретить demo/test режим в production на уровне запуска.

   Сейчас:

   - config.yaml: demo_data: true.
   - Для СЭЭ включены выдуманные месяцы test_months.
   - pages/main.py строит главную на макетных числах.

   При DASHBOARD_ENV=production приложение должно отказываться запускаться,
   если включён demo_data, test_months, временный раздел «СЭЭ 2» или другие
   лабораторные источники. Макеты лучше держать в отдельном dev-профиле
   или закрытом /lab.

5. Убрать запись в один DuckDB-файл из нескольких Gunicorn-процессов.

   Планируются четыре воркера, cron и административные записи в один файл.
   Ретраи снижают частоту ошибок, но не превращают прямую многопроцессную
   запись в штатный режим.

   Рекомендуемая архитектура:

   - DuckDB оставить immutable/read-only аналитическим read model.
   - plan, settings, widgets, журнал действий и указатель опубликованной
     версии вынести в отдельную PostgreSQL-базу приложения.
   - ETL одним процессом атомарно создаёт новый снимок и переключает
     опубликованную версию.

   Минимальный временный вариант — единственный writer-процесс плюс
   межпроцессная очередь/lock; web-воркеры только читают.

6. Реализовать не описание, а работающий backup/restore.

   В DuckDB находятся невосстановимые plan, настройки и виджеты.

   Нужны:

   - Определённые RPO/RTO.
   - Консистентный snapshot под блокировкой writer.
   - Шифрование и отдельное место хранения.
   - Retention.
   - Автоматическая проверка бэкапа.
   - Регулярный тест восстановления на чистом окружении.

7. Обновить Python runtime.

   Локально используется Python 3.12.1. Выбрать для сервера актуальный
   поддерживаемый patch-релиз 3.12 либо проверить проект на актуальной
   ветке Python 3.13/3.14.

8. Добавить полноценную session/CSRF-защиту вместе с входом.

   Для cookie-based SSO нужны Secure, HttpOnly, подходящий SameSite, таймаут
   и ротация сессии, новый session id после входа, logout и re-auth для
   критичных операций. Модифицирующие Dash POST-запросы следует защищать
   CSRF-токеном либо строгой проверкой Origin/Sec-Fetch-Site.


P1 — БЕЗОПАСНОСТЬ И НАДЁЖНОСТЬ ПЕРВОГО СПРИНТА

9. Не возвращать клиенту сырые исключения.

   Сейчас str(e) попадает в ответы plan_input.py, widgets_edit.py и
   settings.py. Это может раскрыть пути, SQL, структуру таблиц и внутренние
   имена. Пользователю нужен безопасный текст и incident id; полный traceback
   должен оставаться только в серверном логе.

10. Добавить HTTP security headers.

    В Nginx пока нет CSP, HSTS, X-Content-Type-Options, защиты от framing,
    Referrer-Policy и Permissions-Policy.

    CSP сначала включить в Report-Only: Dash и текущий inline THEME_BOOT
    потребуют nonce/hash либо переноса скрипта в asset. HSTS включать после
    стабилизации корпоративного сертификата.

11. Настроить trusted proxy и host validation.

    Nginx передаёт Host и X-Forwarded-*, но Flask не настроен на точное число
    доверенных proxy hops и допустимые хосты. Нужны TRUSTED_HOSTS и аккуратный
    ProxyFix; доверять произвольному X-Forwarded-For нельзя.

12. Усилить systemd unit.

    Добавить после проверки совместимости:

    - NoNewPrivileges=true
    - ProtectSystem=strict
    - ProtectHome=true
    - PrivateTmp=true
    - PrivateDevices=true
    - пустой CapabilityBoundingSet
    - RestrictSUIDSGID=true
    - UMask=0077
    - ReadWritePaths только для data/cache/log.

    Код и assets должны быть root-owned и read-only для процесса.

13. Довести Nginx-шаблон до самодостаточного.

    limit_req_zone сейчас только комментарий, но limit_req уже используется.
    Конфигурация не запустится, если администратор забудет вынести зону
    в http{}.

    Также нужны:

    - server_tokens off
    - небольшой client_max_body_size
    - отдельные access/error logs и rotation
    - корпоративный TLS baseline вместо общего HIGH:!aNULL:!MD5
    - явный default server, отклоняющий неизвестный Host.

14. Пересмотреть rate limit с учётом NAT/VPN.

    10 r/s на IP может быть слишком много для одного клиента и слишком мало
    для 70 сотрудников за одним корпоративным proxy. Настроить trusted
    real-IP chain и проверить стартовую пачку Dash callbacks нагрузочным
    тестом.

15. Защитить подключение к PostgreSQL.

    Проверить фактически:

    - отдельная read-only роль только на нужные таблицы;
    - sslmode=verify-full и корпоративный CA;
    - connect_timeout, statement_timeout, application_name;
    - отсутствие прав на DDL и запись;
    - ротация секрета;
    - пароль не попадает в traceback/log.

16. Сделать воспроизводимый lock зависимостей.

    requirements.txt содержит 15 прямых пакетов, тогда как в окружении
    установлено 74. Транзитивные версии при новой установке могут измениться.
    Нужен pyproject.toml плюс uv.lock либо pip-compile --generate-hashes,
    отдельный dev lock и автоматический pip-audit в CI.

17. Вести неизменяемый audit log.

    Для вето, публикации, изменения плана, темы и виджетов записывать:
    реальный пользователь, действие, before/after, timestamp UTC,
    request/correlation id и результат. Текущие таблицы в основном сохраняют
    только последнего автора.

18. Не хранить финансовые величины в DOUBLE, если важна точность.

    Для плана и денежных фактов использовать DECIMAL/NUMERIC либо целое число
    в базовой единице. Floating point допустим для графиков и процентов после
    точного агрегирования.

19. Ограничить риск pickle-кэша.

    FileSystemCache сериализует объекты через pickle. Каталог должен быть
    доступен только служебной учётке, не находиться на общей/NFS-папке
    и не восстанавливаться из недоверенного архива.


ПРОИЗВОДИТЕЛЬНОСТЬ

20. Убрать публикацию из браузерного polling.

    app.py каждые 30 секунд от каждого браузера вызывает publish_due().
    Страница плана запускает ещё один таймер.

    При 70 открытых браузерах это примерно 2,3 polling-callback в секунду;
    каждый делает несколько отдельных открытий DuckDB. Публикацию должен
    выполнять один scheduler/systemd timer. Браузер должен только читать
    один компактный freshness stamp.

21. Свести проверку свежести к одному запросу.

    Сейчас отдельно читаются published version, plan stamp, due versions,
    due plan, pending summary и last update. Лучше завести одну строку
    app_state с display_version, published_at, pending_count и обновлять её
    транзакционно writer-процессом.

22. Не допускать параллельных ETL-прогонов.

    Cron запускается каждые пять минут без flock. Если один полный прогон
    займёт больше пяти минут, стартует второй. Использовать systemd
    timer/service или flock -n, фиксировать skipped overlap и длительность.

23. Перейти от полного пересчёта к инкрементальному только при
    подтверждённом росте.

    Сейчас изменение любой таблицы перечитывает все месячные таблицы.
    Для текущего объёма это приемлемо. Триггер для усложнения: ETL перестал
    укладываться в заданный SLA или заметен в pg_stat_statements. Тогда
    загружать только новые/изменённые месяцы и хранить fingerprint
    по таблице/партиции.

24. Не использовать SELECT * в source query.

    etl/load_budget.py объединяет все колонки всех таблиц. Выбирать только
    region_name, report_date и семь используемых показателей. Проверить
    EXPLAIN (ANALYZE, BUFFERS) вместе с DBA.

25. Не считать pg_stat_user_tables источником истины о свежести.

    n_live_tup является оценкой. Лучше watermark/updated_at от владельца
    источника, CDC или журнал загрузок. Пока его нет — периодический
    принудительный полный refresh и независимая сверка последних дат/строк.

26. Сохранить текущую lazy-rendering стратегию.

    Отложенная постройка диаграмм и один проход по годам сделаны хорошо.
    Не переносить всё в SQL/Redis без профиля. Текущий снимок читается
    примерно за 61 мс; сначала измерить p50/p95 каждого callback под
    70 параллельными сессиями.

27. Сравнить файловый кэш с process-local snapshot.

    После отключения demo размер снимка станет меньше текущих 15,7 МБ.
    Четыре копии в памяти могут оказаться дешевле постоянной
    pickle-десериализации. Решение принимать по RSS и p95. Redis для
    70 пользователей пока не обязателен.

28. Подбирать Gunicorn workers нагрузочным тестом.

    Число 4 не должно быть нижней границей по умолчанию. Plotly/Pandas дают
    CPU-нагрузку, а DuckDB — lock contention. Проверить 2/4/6 workers по p95,
    RSS, CPU и частоте retry. Добавить max-requests с jitter, graceful timeout
    и отдельный readiness check.

29. Настроить ротацию логов.

    etl.log и cron.log растут без ограничения. Лучше systemd journal или
    logrotate, retention и лимит диска.


АРХИТЕКТУРА

30. Сохранить монолит, но разделить control plane и analytics plane.

    Микросервисы, Kubernetes и отдельный Redis сейчас не нужны.

    Полезная граница:

    - ETL/analytics: source -> immutable versioned snapshot -> DuckDB.
    - Control plane: пользователи, роли, plan, settings, widgets, audit,
      current version -> PostgreSQL.
    - Dash: только orchestration, чтение и визуализация.
    - Scheduler: один процесс, публикация и ETL.

31. Разделить core/data.py.

    Сейчас модуль одновременно отвечает за соединения, retry, конфигурацию,
    кэш, SQL, бизнес-агрегации и форматирование. Рекомендуемые модули:
    storage, facts_repository, aggregations, formatting, config.

32. Разбить крупные UI-модули по ответственности.

    - core/charts.py — 1918 строк.
    - pages/section.py — 1462 строки.
    - core/data.py — 1083 строки.
    - pages/main.py — 971 строка.

    Делить не по числу строк, а по причинам изменения: chart families,
    section layout, section callbacks, drilldown, mockup/main presentation.

33. Вынести бизнес-операции из callbacks.

    Callback должен: проверить identity/role -> валидировать DTO -> вызвать
    use case -> вернуть UI result. Публикация, вето, изменение виджета и темы
    должны быть отдельными сервисами, не зависеть от Dash context и
    тестироваться обычными unit tests.

34. Ввести формальную схему конфигурации.

    config.yaml одновременно содержит показатели, разделы, дизайн, размеры,
    demo-флаги и наборы виджетов. Нужна Pydantic/JSON Schema проверка при
    запуске, ссылки между показателями и environment overlays base/dev/prod.

35. Сделать явные миграции.

    Сейчас миграции выполняются при импорте app.py, а ошибка логируется
    и приложение продолжает работу. Миграции должны быть отдельной
    командой/ExecStartPre, иметь schema_version, backup перед изменением
    и останавливать deployment при неуспехе.

36. Формализовать state machine публикации.

    Статусы pending/published/rejected/superseded оформить как одну модель
    переходов. Добавить инварианты:

    - опубликована ровно одна версия;
    - нельзя публиковать rejected;
    - версия не откатывается назад случайно;
    - план публикуется атомарно;
    - повторная команда идемпотентна.

37. Добавить ограничения схемы.

    Primary/unique/check constraints для version, widget (page,id),
    (page,position), разрешённых статусов и уникального draft плана.
    max(id)+1 заменить на sequence/identity после переноса в PostgreSQL.

38. Использовать timezone-aware datetime.

    Сейчас публикация зависит от datetime.now() и часового пояса сервера.
    Хранить timestamps в UTC, бизнес-время публикации задавать явной ZoneInfo,
    а NTP/timezone проверять readiness-проверкой.

39. Изолировать dev-инструменты.

    etl/load_test_data.py содержит абсолютный Windows-путь. Генераторы и
    demo loaders перенести в dev-only tooling, путь передавать аргументом CLI,
    а production package не должен импортировать mock-модули.

40. Сократить дублирование документации.

    Документация подробная, но уже расходится с деревом: архитектурный раздел
    ROADMAP всё ещё перечисляет удалённые explore-страницы. Оставить короткий
    актуальный README, ADR для важных решений и автоматически проверяемую
    схему/config; исторические отчёты вынести отдельно.


ТЕСТЫ, CI И ЭКСПЛУАТАЦИЯ

41. Добавить CI на Linux — целевую серверную ОС.

    Минимум: unit/integration tests, config validation, lint, type check,
    pip check, pip-audit, secret scan и сборка чистого окружения по lock-файлу.

42. Добавить security integration tests.

    Проверять прямые POST к Dash callback endpoint, обход скрытых страниц,
    SQL payload в page/key, CSRF/origin, Host header, security headers
    и отсутствие внутренних исключений в ответе.

43. Добавить конкурентные и восстановительные тесты.

    Отдельно проверить ETL + публикацию + административную запись, падение
    процесса внутри транзакции, повтор команды, запуск двух ETL и
    восстановление из бэкапа.

44. Добавить нагрузочный baseline.

    Сценарий: 70 пользователей через один VPN/NAT, одновременное открытие
    раздела, смена вкладки и публикация. Собирать p50/p95/p99, RSS worker,
    CPU, cache hit rate, DuckDB retry count и размер ответа Plotly.

45. Добавить web-observability до production.

    Сейчас Sentry подключён только к ETL. Для сайта нужны ошибки, latency
    callbacks, 4xx/5xx, lock retries, возраст последнего успешного ETL
    и опубликованной версии. Перед отправкой настроить scrub финансовых
    значений, usernames и DSN.

46. Добавить /health/live и /health/ready.

    live — процесс отвечает. ready — схема актуальна, есть опубликованная
    версия, ETL не просрочен, DuckDB читается, production guard пройден.
    Не включать туда тяжёлые запросы.


СИЛЬНЫЕ СТОРОНЫ, КОТОРЫЕ СТОИТ СОХРАНИТЬ

- Единая длинная таблица фактов и «узкая талия» между источниками и UI.
- Read-only роль к исходной БД как принцип.
- Транзакционная загрузка снимка и независимая сверка сумм.
- Версионирование опубликованных данных.
- Lazy rendering и устранённые N+1-проходы по годам.
- Локальные assets без зависимости от внешнего CDN.
- .env не обнаружен ни в tracked-файлах, ни в истории.
- Хорошо зафиксированные причины нетривиальных решений.


ГЛАВНАЯ АРХИТЕКТУРНАЯ РЕКОМЕНДАЦИЯ

Перед production сделать Dash строго авторизованным read-heavy приложением,
вынести изменяемое состояние из многопроцессного DuckDB и оставить ровно
одного владельца публикации/ETL. Остальные улучшения можно выполнять
постепенно, по замерам.
