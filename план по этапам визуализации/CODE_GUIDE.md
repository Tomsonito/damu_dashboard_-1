# Как устроен код

Справочник по коду проекта: какой файл за что отвечает, что делает каждая
функция и куда лезть, когда нужно что-то поменять.

Разделы идут **по этапам дорожной карты**: в каком этапе часть появилась,
в том разделе она и описана. Если файл рос в несколько этапов (например,
`core/data.py`), у него несколько разделов — в каждом этапе свой.
Сквозные справочники «что где менять», «как запускать», «что сломается» — в конце.

Дорожная карта — в [ROADMAP.md](../ROADMAP.md). Здесь только про код.

> **Как помечать важное.** Ставьте в начале строки метку и дописывайте заметку
> своими словами. Метки набираются с клавиатуры, лезть за эмодзи не нужно:
>
> | Метка | Смысл |
> |---|---|
> | `@@` | вернуться и разобраться |
> | `??` | непонятно, спросить |
> | `!!` | осторожно, тут легко сломать |
>
> Найти все пометки разом — `Ctrl+F` и поиск по `@@`, внизу окна поиска будет
> счётчик совпадений и стрелки для перехода между ними.
>
> Пометки лежат прямо в тексте, поэтому попадают в git вместе с ним: переживут
> переустановку редактора и будут видны с другого компьютера.
>
> Чтобы выделить кусок **цветом**, оберните его так: `<mark>важное место</mark>` —
> в предпросмотре (`Ctrl+Shift+V`) он подсветится жёлтым.

@@ *пример пометки — эту строку можно удалить*

## Сквозная картина

### Поток данных

Это **два разных процесса**, которые происходят в разное время. Их легко перепутать
и решить, что данные текут из базы в браузер непрерывно. Это не так.
@@
```
═══ ШАГ 1. Загрузка — python -m etl.run; на этапе 5 это будет делать cron ═══

  PostgreSQL (боевая БД, только чтение)
        │
        │   отпечаток источника не менялся? — выход за секунды
        │   менялся? — пересчёт, сверка, новая версия «ждёт публикации»
        ▼
  data/analytics.duckdb        хранилище: таблицы facts, versions, plan


═══ ШАГ 1½. Публикация — шлюз 9:00 (этап 4, core/publish.py) ═══

  свежая версия и черновики плана лежат в хранилище, но сайту не видны
        │
        │   в ближайшие 9:00 (или при первой проверке после) — публикуются;
        │   до этого админ может отменить черновик или забраковать версию
        ▼
  статус «опубликована» — только такое видит витрина


═══ ШАГ 2. Показ — происходит сам, при каждом открытии страницы ═══

  data/analytics.duckdb
        │
        │   core/data.py — единственная дверь к данным (через кэш)
        ▼
  pages/main.py                собирает карточки и график
        │
        ▼
  браузер, localhost:8050 — раз в 30 сек публикует дозревшее и сверяет
                            display-версию; перерисовывается при смене
```

**Шаг 1 выполняется по расписанию** — сейчас руками, на этапе 5 его будет дёргать
cron каждые 5 минут. Благодаря отпечатку источника холостой прогон стоит секунду.

**Шаг 2 выполняется постоянно** — каждый раз, когда кто-то открывает страницу или
двигает фильтр. Боевая база при этом не трогается вообще: дашборд ходит только
в свой DuckDB-файл и даже не знает, откуда тот наполняется.

**Почему не читать боевую БД прямо со страницы?** Три причины. Семьдесят зрителей
дёргали бы чужую рабочую систему на каждый клик. Сайт зависел бы от её доступности —
а так он показывает последние загруженные цифры, даже если база легла. И разбор
хрупкий: если источник изменит структуру, сломается только шаг 1,
и сайт продолжит показывать прошлые цифры вместо того, чтобы упасть.

До подключения БД те же два шага выглядели как «разбор Excel → facts.csv → показ»:
принцип разделения не менялся, поменялся только источник.

**Главное правило:** страницы никогда не читают файлы и базы напрямую. Только через
`core/data.py`. Из-за этого при смене источника (Excel → БД → DuckDB) переписывается
один файл, а `pages/` остаётся нетронутым.

## Этап 0 — каркас

### `app.py` — точка входа

Здесь **нет никакого содержимого страниц**. Только рама:

```python
app = dash.Dash(__name__, use_pages=True, external_stylesheets=[dbc.themes.BOOTSTRAP])
```

- `use_pages=True` — страницы искать в папке `pages/`
- `external_stylesheets` — подключить Bootstrap

```python
server = app.server
```

Достаёт изнутри Dash обычное Flask-приложение. На этапе 5 за эту строку будет
цепляться Gunicorn; с этапа 3 к `server` привязывается кэш —
`cache.init_app(server)`, зачем это обязательно, см. раздел этапа 3.

```python
app.layout = html.Div([
    dbc.NavbarSimple(brand='Дашборд Даму', color='dark', dark=True, fluid=True),
    dash.page_container,
])
```

То, что видно на **каждой** странице: тёмная шапка, а под ней `page_container` —
«дырка», куда Dash подставляет содержимое текущей страницы.

```python
app.run(debug=True, dev_tools_hot_reload=False)
```

`debug=True` даёт понятные сообщения об ошибках прямо в браузере.

`dev_tools_hot_reload=False` **выключает автоперезагрузку**, и это осознанно.
Со включённой Dash сам обновлял страницу при любой правке файла — и **все выбранные
фильтры слетали на исходные**. Она же была причиной счётчика ошибок в панели Dash:
браузер держал старую страницу и обращался к коллбэкам по устаревшим адресам.

Цена: после правки кода страницу нужно обновить самому, `F5`.

## Этап 1 — фронтенд на реальных данных

Что появилось: общая таблица фактов, разборщик Excel, реестр показателей,
слой данных, главный экран и 16 видов диаграмм (17-й добавился на этапе 4).

### Общая таблица фактов

Форма, к которой любой разборщик приводит свой источник, каким бы кривым тот ни был.

#### Главное: одна строка = одно предложение

Вот настоящая строка таблицы фактов (времён Excel-выгрузки):

```
indicator    = 'active_smb'
report_year  = 2025
date         = '2025-10-01'
period       = 'на дату'
region       = 'Атырауская'
instrument   = (пусто)
program      = (пусто)
is_total     = False
value        = 65346.0
source_file  = 'Основные показатели деятельности субъектов МСП.xlsx'
loaded_at    = '2026-07-22T12:50:10'
```

Читается как обычная фраза:

> **Действующих субъектов МСП** в **Атырауской области** **на 1 октября 2025 года**
> было **65 346**. Взято из **такого-то файла**, разобрано **тогда-то**.

Если строка не читается такой фразой — значит в разборе ошибка. Это простая и надёжная
проверка себя.

#### Четыре группы колонок

Все одиннадцать колонок отвечают на четыре вопроса:

| Вопрос | Колонки | Зачем |
|---|---|---|
| **Что измеряем?** | `indicator`, `period` | какой именно показатель и какого он типа |
| **Когда?** | `report_year`, `date` | к какому периоду относится число |
| **В каком разрезе?** | `region`, `instrument`, `program` | по какому срезу разложено |
| **Само число** | `value` | единственная колонка с цифрой |
| *(служебное)* | `is_total`, `source_file`, `loaded_at` | защита от ошибок и прослеживаемость |

Колонок-разрезов может быть сколько угодно, а колонка со значением **всегда одна**.
В этом вся идея.

#### Что было в Excel и что стало

Было — двухэтажная шапка, регион в строках, показатели размазаны по колонкам:

```
                  На 1 октября 2025 г.        На 1 октября 2024 г.
                зарегистр.   действующих   зарегистр.   действующих
Атырауская        70239         65346         68666        62537
```

Стало — четыре отдельные строки, у каждой своё число:

```
registered_smb  2025  Атырауская  70239
active_smb      2025  Атырауская  65346
registered_smb  2024  Атырауская  68666
active_smb      2024  Атырауская  62537
```

Строк стало больше, зато **все они одинаковой формы**. Именно поэтому любой новый
источник ляжет сюда же, не сломав ни одного виджета: смена Excel → БД это подтвердила.

#### Откуда бралось 168 строк

```
21 строка (20 областей + итог по РК)
 ×  8 сочетаний (4 показателя × 2 года)
= 168
```

Про одну Атыраускую область в таблице лежало ровно 8 строк:

```
     indicator  report_year       date  period     value
    active_smb         2024 2024-10-01 на дату   62537.0
    active_smb         2025 2025-10-01 на дату   65346.0
      employed         2024 2024-10-01 на дату  152838.0
      employed         2025 2025-10-01 на дату  141993.0
        output         2024 2024-09-30     ytd 4153609.0
        output         2025 2025-09-30     ytd 3831313.0
registered_smb         2024 2024-10-01 на дату   68666.0
registered_smb         2025 2025-10-01 на дату   70239.0
```

(Сейчас в хранилище 7 000 строк из БД — та же форма: 20 областей × 50 месяцев
× 7 показателей.)

#### Тонкие места

**Зачем и `report_year`, и `date` — не одно ли это?**

Нет, и разница видна прямо в таблице выше. У показателя `output` за 2025 год дата
**`2025-09-30`**, а у остальных — **`2025-10-01`**. В источнике так и написано: одни цифры
«на 1 октября», другие «за январь-сентябрь».

Если фильтровать по `date`, показатели одного и того же отчёта разъедутся по разным датам
и на экран попадут не все. `report_year` склеивает то, что относится к одному отчётному
периоду. Поэтому фильтр на странице работает по `report_year`, а `date` хранится, чтобы
не потерять точность источника.

**`period`: `на дату` против `ytd`**

- `на дату` — **срез**: сколько чего существует в конкретный день. Столько-то компаний, столько-то занятых
- `ytd` (year to date) — **накопление с начала года**: выпуск продукции за январь-сентябрь суммарно

Разница не косметическая. Накопленные величины **нельзя складывать между периодами**:
если бы у нас были ytd за март и за июнь, их сумма была бы бессмыслицей — июньское число
уже включает мартовское. А срезы нельзя усреднять как потоки.

Пока в расчётах эта колонка не участвует, но записана осознанно: когда дойдёт до сравнений
периодов, она не даст ошибиться.

**Почему `instrument` и `program` пустые**

Схема одна на все источники. В текущих данных разрез только по регионам, поэтому две
колонки пустуют. Когда придёт источник с разбивкой по инструментам, всё будет наоборот:
`instrument` заполнится, а `region` останется пустым.

Схема при этом **не меняется** — в этом и смысл. (В CSV пустые ячейки читаются pandas
как `NaN`, а не как пустая строка — на фильтры это не влияет.)

**Почему итог хранится, а не выбрасывается**

«Республика Казахстан» — это сумма, а не 21-й регион. Хранить её как обычную строку нельзя:
любая сумма по таблице удвоится.

Но и выбрасывать не стоит по двум причинам. Во-первых, это **официальная цифра источника** —
если в следующей выгрузке она не сойдётся с суммой областей, показывать надо ту, что
написана в отчёте, а не свою. Во-вторых, на ней держится проверка `check_totals`.

Отсюда `is_total`: строка лежит в таблице, но одним фильтром убирается из расчётов.
(В данных из БД строки-итога нет — тогда итог по стране складывается из регионов,
см. `_country_totals`.)

**Зачем `source_file` и `loaded_at`**

Источников будет много. Когда на экране появится странная цифра — а она однажды
появится — эти две колонки за секунду скажут, откуда она пришла и когда разбиралась.
Без них поиск занял бы час.

#### Два принципа, ради которых всё это

**Показатели растут строками, а не колонками.** Новый показатель — это новые строки.
Схема таблицы не меняется, код страниц не трогается.

**Итоги помечаются, а не выбрасываются.** `is_total` не даёт сложить «Республику Казахстан»
вместе с областями и получить двойной счёт.

### `etl/parse_msp.py` — разборщик Excel

Сейчас не используется (данные едут из БД), но файл рабочий — пригодится,
когда придёт следующая ручная выгрузка.

Запуск **из корня проекта**:

```bash
python -m etl.parse_msp
```

Именно `-m etl.parse_msp`, а не `python etl/parse_msp.py` — иначе не найдутся импорты из `core/`.

#### Константы

| Имя | Зачем |
|---|---|
| `SRC_PATH` | где лежит оригинал |
| `OUT_PATH` | куда писать результат |
| `TOTAL_LABEL` | `"Республика Казахстан"` — по этой строке ищем начало блоков |
| `ROWS_PER_BLOCK` | `21` — итог по РК плюс 20 регионов |
| `COLUMNS` | список канонических колонок, в этом порядке пишется CSV |
| `SPEC` | **самое важное** — расшифровка кривой шапки |

**Про `SPEC`.** Шапка в файле двухэтажная, с объединёнными ячейками, и подписи в двух блоках
написаны по-разному («2025 г.» против «2025г.»). Разбирать её автоматически — напрашиваться на
молчаливую ошибку. Поэтому мы описываем вручную, что лежит в каждой колонке:

```python
(1, 2, "active_smb", 2025, "2025-10-01", "на дату"),
#  │  │       │        │         │            └─ тип величины
#  │  │       │        │         └─ точная дата
#  │  │       │        └─ отчётный год
#  │  │       └─ код показателя
#  │  └─ номер колонки в блоке (1 = B, 2 = C, 3 = D, 4 = E)
#  └─ номер блока (1 — верхний, 2 — после строки «Продолжение»)
```

Придёт новая выгрузка за другой квартал — правите только `SPEC`, остальной код не трогаете.

#### `find_block_starts(raw) -> list[int]`

Находит, с каких строк начинаются два блока данных.

Ищет **не по номерам строк, а по строке «Республика Казахстан»**. Если в следующей выгрузке
шапка съедет на пару строк, разбор всё равно попадёт куда надо.

Если блоков нашлось не два — бросает ошибку с текстом «Формат файла изменился?». Лучше
громкий отказ, чем тихо неверные цифры.

#### `parse(src=SRC_PATH) -> pd.DataFrame`

Основная работа. Читает Excel целиком без шапки (`header=None`), проходит по обоим блокам,
по каждой строке `SPEC` собирает записи.

Что делает попутно:

- **чистит названия регионов** через `.strip()` — в файле у части названий хвостовой пробел
  (`'Актюбинская '`), глазом не видно, а группировку ломает
- **пропускает пустые ячейки** — `if pd.isna(value): continue`
- **помечает итог** — `is_total = region == TOTAL_LABEL`
- **проставляет источник и время** — чтобы потом найти виновника странной цифры

Возвращает готовый DataFrame, отсортированный по показателю, году и региону.

#### `check_totals(df) -> list[str]`

Проверяет, что сумма регионов сходится со строкой итога — по каждому показателю и году.

Это **дешёвая защита от съехавшей шапки**. Если разбор попадёт не в ту колонку, сверка почти
наверняка развалится, и вы узнаете об этом сразу, а не из отчёта руководству.

Возвращает список проблем. Пустой список = всё хорошо.

#### `main() -> None`

Собирает всё вместе: разобрать → проверить → записать.

**Если проверка не прошла — файл не записывается вообще** (`raise SystemExit`). Лучше остаться
со старыми данными, чем перезаписать их испорченными.

### `config.yaml` — реестр показателей

Здесь описано, как показывать каждый показатель. **Добавить показатель = добавить блок сюда**,
код при этом не меняется.

```yaml
output:
  title: "Выпуск продукции субъектами МСП"   # полное имя: заголовок графика
  short: "Выпуск продукции"                  # короткое: подпись на карточке
  unit: "млн тенге"                          # единица в исходных данных
  kind: flow_ytd                             # stock — срез на дату
                                             # flow_ytd — накоплено с начала года
  divisor: 1000000                           # на сколько делить перед показом
  display_unit: "трлн ₸"                     # что писать после числа
  decimals: 2                                # знаков после запятой
  agg: last                                  # как сворачивать месяцы в год
```

`divisor` + `display_unit` — это перевод масштаба. В данных лежит `73180136` млн тенге,
на экране показывается `73.18 трлн ₸`. Сырое число в таблице не трогается — меняется
только вид.

`kind` пока нигде не используется в расчётах, но записан осознанно: «на дату» и
«накоплено с начала года» — принципиально разные величины, их нельзя складывать между
периодами. Когда дойдёт до сравнений, эта пометка не даст ошибиться.

Внизу файла:

```yaml
kpi_order: [budget_allocated, budget_spent, budget_execution, subsidies_issued, workplaces_created]
```

Порядок карточек на экране. Поменяли местами — карточки переставились.

Там же: `macroregions` (группировка областей для иерархических диаграмм),
`charts.min_slice_percent` (минимальный размер сектора) и `geo` (файл границ
для карты и соответствие названий областей).

### `core/data.py` — базовые функции слоя данных

Все страницы берут данные только отсюда. Ни одна страница не открывает файлы сама.
(Как данные читаются и кэшируются — в разделе этапа 3; здесь — что функции считают.)

#### `_aggregate(df, indicator, by)` — свёртка месяцев в год

Источники разной частоты: выгрузка Excel давала одну строку на год, таблицы из БД —
двенадцать, по месяцам. Складывать их одинаково нельзя, и правило у каждого показателя
своё — поле `agg` в `config.yaml`:

| `agg` | Как сворачивает | Для чего |
|---|---|---|
| `sum` | складывает | потоки: выделено, освоено, субсидии |
| `last` | берёт на последнюю дату | срезы: сколько МСП существует |
| `mean` | усредняет | средний срок освоения |

Без этого на графике каждый регион появился бы двенадцать раз.

#### `_country_totals(df, year)` — итог по стране

Два случая. Если в источнике есть готовая строка-итог (в выгрузках статистики была
«Республика Казахстан») — берём её: официальная цифра важнее нашей суммы, и если они
разойдутся, показать надо источник.

Если строки-итога нет — а в данных из БД её и не бывает — складываем регионы сами,
по тому же правилу `agg`.

#### `get_kpi(year) -> pd.DataFrame`

Данные для карточек: итоги по стране за год и изменение к предыдущему году.

Для каждого показателя из `kpi_order` возвращает строку с полями:

| Поле | Что в нём |
|---|---|
| `indicator` | код показателя |
| `short` | подпись для карточки |
| `title` | полное название |
| `value` | сырое число |
| `text` | уже отформатированное, готовое к показу |
| `change_pct` | изменение к прошлому году, или `None` |
| `change_kind` | `pct` — проценты, `pp` — процентные пункты (этап 4) |

`change_pct` равен `None`, когда данных за предыдущий год нет — карточка тогда пишет
«нет данных за прошлый год» вместо того, чтобы сломаться. Показатели, которых нет
в данных, пропускаются молча — реестр может описывать больше, чем загружено.

С этапа 4 умеет **производные карточки** — см. раздел этапа 4.

#### `get_regions(indicator, year, limit=None, regions=None) -> pd.DataFrame`

Значения по регионам за год, по убыванию. **Строка итога исключена** — иначе «Республика
Казахстан» была бы самым большим столбиком на графике и всё остальное сплющилось бы.

`limit` ограничивает выдачу (топ-10, топ-5). `regions` — показать только перечисленные
регионы; `None` или пустой список означает «все». Так работает фильтр регионов на странице.

#### `get_region_choices() -> list[str]`

Регионы по алфавиту для фильтра, без строки итога. Список не зашит в код — читается
из данных: появится новый регион, сам появится и в фильтре.

#### `get_region_dynamics(indicator, regions=None) -> pd.DataFrame`

Показатель по регионам **за все годы сразу** — колонки `region`, `report_year`, `value`.
Нужна диаграммам «Сравнение лет» и «Наклон».

#### `get_change(indicator, year, regions)` — изменение к прошлому году

Колонки `region, prev, current, delta`. Нужна каскаду.

Сравнивает именно `year` и `year - 1`, а **не два последних года в данных**. Последний
год в источнике почти всегда неполный — у нас 2026-й обрывается на июле, — и сравнение
с ним показало бы обвал там, где просто ещё не наступили остальные месяцы.

#### `get_table(year, regions=None) -> pd.DataFrame`

Широкая таблица для экрана: регион в строке, показатели в колонках.

Это **единственное место, где длинная таблица разворачивается в широкую** — и только
для показа. В хранилище всё остаётся длинным. Порядок колонок берётся из `kpi_order`
в конфиге (производные показатели, которых нет в данных, пропускаются).

#### `get_indicator_meta(indicator) -> dict`

Достаёт описание одного показателя из конфига. Используется везде, где нужно узнать
единицу или масштаб.

#### `get_indicator_choices() -> list[dict]`

Готовый список для выпадающего фильтра. Показываются только показатели,
по которым **реально есть данные**: реестр может описывать больше, чем загружено,
и предлагать заведомо пустой пункт незачем.

#### `get_years() -> list[int]`

Годы, за которые есть данные, свежий первым: `[2026, 2025, 2024, 2023, 2022]`.

Не зашит в код — читается из данных. Появится новый год — сам появится в фильтре.

#### `format_value(value, indicator) -> str`

Превращает число в строку для показа: делит на `divisor`, округляет до `decimals`,
расставляет разряды, дописывает единицу.

```
format_value(73180136, "output")   →  "73.18 трлн ₸"
format_value(4522420, "employed")  →  "4 522 420 чел."
```

Разряды разделяются **неразрывным пробелом** (`\xa0`), а не обычным. Обычный пробел браузер
может перенести на другую строку, и число разорвётся пополам посреди строки.

### `pages/main.py` — главный экран

(Автообновление без F5 добавилось на этапе 3 — см. его раздел.)

#### `dash.register_page(...)`

```python
dash.register_page(__name__, path="/", name="Главная", title="Дашборд Даму")
```

Регистрирует файл как страницу по адресу `/`. `title` — подпись на вкладке браузера.

#### `kpi_card(row) -> dbc.Card`

Рисует одну карточку: подпись, крупное число, изменение к прошлому году.

Стрелка и цвет выбираются по знаку: рост — `▲` зелёным, падение — `▼` красным.
Если `change_pct` пустой — вместо стрелки серая надпись «нет данных за прошлый год».
У карточки-доли изменение подписывается «п.п.», а не «%» (этап 4).

Обычная функция, не коллбэк: получает строку данных, возвращает готовый компонент.

#### `layout(**kwargs)`

Каркас страницы: заголовок, фильтры, пустой ряд под карточки, пустой график, таблица.

**Это функция, а не переменная — и это важно.** Dash вызывает её при каждом открытии
страницы. Если бы `layout` был обычной переменной, список годов в фильтре собрался бы
один раз при запуске приложения и с тех пор не менялся, даже после перегона данных.

Ещё одна деталь: `dbc.Row(id="kpi-row")` и `dcc.Graph(id="regions-chart")` создаются
**пустыми**. Наполняют их коллбэки. Здесь только места под содержимое и их имена.

Если хранилища данных нет — вместо страницы показывается жёлтая плашка
с подсказкой, что запустить. Приложение не падает.

#### `render_kpi(year, _version)` — коллбэк карточек

```python
@callback(Output("kpi-row", "children"), Input("filter-year", "value"), ...)
```

Читается так: **«когда меняется `value` у фильтра года — пересобери `children` у блока
с карточками»**.

Dash сам следит за фильтром и сам вызывает функцию. Вручную её никто не дёргает.
Вызывается ещё и при первой загрузке страницы — поэтому карточки появляются сразу.

Внутри: взять данные через `data.get_kpi()`, сделать из каждой строки карточку.
Ряд делится между карточками поровну (`dbc.Col` без ширины), сколько бы их ни было;
на узких экранах карточки встают в столбик (`xs=12`).

#### `toggle_log(chart_type)` — галка логарифма знает про себя

Гасит галку на видах, которые логарифм не умеют, и дописывает к подписи
«(этот вид её не поддерживает)».

Зачем: логарифм умеют два вида из семнадцати, а галка нажималась на всех.
Человек её ставил на «Полосах» и не понимал, почему график не изменился —
`build()` молча игнорировал флаг. Теперь видно сразу.

!! **Список видов в подписи вписывать нельзя.** Раньше там было
«(работает на «Точках» и «Ящике»)» — обычная фраза, которая дублировала
реестр. Добавили бы третий вид с `log_ok=True` — и подпись стала бы враньём,
причём молча: ошибка не в коде, а в русском тексте, тесты такое не ловят.
Теперь и доступность, и текст берутся из `charts.supports_log()`.

**Выбор запоминается.** Переключились с «Точек» на «Полосы» — галка погасла,
но осталась отмеченной; вернулись на «Ящик» — логарифм снова применился.
Проверено в браузере.

#### `render_chart(...)` — коллбэк в одну строку

Вся отрисовка вынесена в `core/charts.py`, здесь остаётся только передать выбор
пользователя.

**Как это выглядело раньше (и почему вынесли).** Пока видов было четыре, отрисовка
жила прямо здесь — одна функция с лесенкой `if / elif / else` на все виды. С каждым
новым видом лесенка росла, и `pages/main.py` превращался в свалку из отрисовки
и вёрстки. Поэтому диаграммы переехали в реестр `core/charts.py`.

#### `render_table(year, regions, _version)` — коллбэк таблицы

Наполняет таблицу под графиком: и данные, и заголовки колонок сразу
(`Output("regions-table", "data")` и `Output("regions-table", "columns")`).

Заголовки собираются из конфига — «Занятых, человек», — поэтому переименование
показателя в `config.yaml` меняет и шапку таблицы.

Два неочевидных места:

- `"type": "numeric"` у колонок обязателен — без него сортировка по клику была бы
  **алфавитной**: 1 000 000 встал бы раньше 200, потому что «1» < «2» как буквы
- формат `TABLE_NUM_FORMAT` расставляет разряды пробелами прямо в таблице, при этом
  внутри данные остаются числами и сортировка работает правильно

Реагирует на год и фильтр регионов. Показатель и вид диаграммы на таблицу не влияют —
она всегда показывает все колонки.

### `core/charts.py` — реестр диаграмм

**Добавить вид диаграммы = написать одну функцию с декоратором `@chart`.**
Больше нигде править не нужно: и список в выпадающем меню, и разбор выбора
строятся из реестра автоматически.

```python
@chart("box", "Ящик — разброс по макрорегионам", log_ok=True)
def _box(ctx: Ctx) -> go.Figure:
    df = ctx.scaled(data.get_regions_grouped(ctx.indicator, ctx.year, regions=ctx.regions))
    fig = px.box(df, x="macroregion", y="shown", points="all", hover_name="region",
                 labels={"shown": ctx.unit, "macroregion": ""},
                 title=f"{ctx.title} — разброс внутри макрорегионов")
    fig.update_traces(pointpos=0, jitter=0.4, width=0.5)
    if ctx.log:
        fig.update_yaxes(type="log")
    return fig
```

Как это устроено:

- **`_REGISTRY`** — словарь `код вида → {подпись, функция, log_ok}`. Заполняется
  декоратором в момент импорта модуля
- **`@chart(value, label, log_ok=False)`** — кладёт функцию в реестр. `value` уходит
  в HTML, `label` видит пользователь, `log_ok` разрешает логарифмическую шкалу
- **`Ctx`** — то, что диаграмма получает: показатель, год, список регионов, флаг `log`.
  Плюс готовые `meta`, `unit`, `title` и метод `scaled()`, который добавляет колонки
  `shown` (значение в масштабе показа) и `текст` (оно же строкой для подписей)
- **`get_choices()`** — собирает список для выпадающего меню
- **`supports_log(вид)`** — умеет ли вид логарифм. На этом держится галка
  логарифма: `toggle_log` в `pages/main.py` гасит её на видах без `log_ok`
- **`build()`** — находит нужную функцию, вызывает и навешивает **общее оформление**:
  поля, фон, высоту 700 (если вид не задал свою) и `separators` — русский формат
  чисел, запятая для дробей и неразрывный пробел для разрядов. Без него plotly
  писал бы по-английски: `454,416.0`
- **`_message()`** — пустая фигура с текстом. Возвращается, когда рисовать нечего:
  нет второго года для каскада, нет файла карты. Лучше объяснение на экране, чем падение

#### Что делать с огромным разрывом между регионами

У Алматы 454 тысячи субъектов, у Ұлытау — 19 тысяч, разница в 23 раза.
По выпуску продукции разрыв ещё больше, в 80 раз. На одной линейной шкале мелкие
регионы превращаются в невидимые полоски. Приёмы против этого:

**1. Подписи значений.** Самое простое и честное: полоска маленькая, но число
написано рядом. Ничего не теряется. Включено на полосах, точках и панелях.

**2. Логарифмическая шкала** — галка под фильтром регионов. Сжимает разрыв так,
что 19 тысяч и 454 тысячи видны одинаково хорошо.

Но она работает **только на «Точках» и «Ящике»**, и это принципиально.
На столбцах логарифм врёт: длина столбца обязана быть пропорциональна значению
и отсчитываться от нуля, а логарифм это ломает — столбец вдвое длиннее будет
означать значение в десять раз больше. Точка ничего не обещает про ноль,
поэтому на ней логарифм честен.

Кто умеет логарифм, помечено в реестре флагом `log_ok=True`. На видах без
этого флага галка **гаснет** — за это отвечает коллбэк `toggle_log`
в `pages/main.py`, см. раздел про главный экран.

**3. Панели по макрорегионам** — вид «Панели», у каждой панели своя шкала.
Ұлытау сравнивается с Карагандинской внутри своей панели, а не теряется
рядом с Алматы. Ключ к этому — одна строка `fig.update_xaxes(matches=None)`,
которая отвязывает оси подграфиков друг от друга.

**4. Минимальный размер сектора** — для круговой, плиток, лучей и сосулек.
Осознанный компромисс, см. следующий раздел.

#### Круговая, плитки, лучи, сосульки — и компромисс с размером

На этих четырёх видах размер задаётся площадью, и мелкий регион превращается
в полоску, куда подпись не влезает: «Ұлытау 19 612» вылезала за круг поверх
соседей.

**Принято решение подтягивать мелкие сектора до 10 % от самого крупного.**
Порог — `charts.min_slice_percent` в `config.yaml`, `0` возвращает строгую
пропорциональность.

Это компромисс: площадь перестаёт точно соответствовать значению. Чтобы он
не превратился в обман, соблюдаются два правила:

- **числа в подписи и подсказке — всегда настоящие**, не подтянутые
- в заголовке появляется пометка «у N регионов сектор увеличен до 10 %»

Как это сделано:

| Функция | Что делает |
|---|---|
| `_size_floor(values)` | считает порог: максимум × процент из конфига |
| `_label(value, ctx)` | настоящее значение строкой — разряды, единица |
| `_adjusted_note(raised, ctx)` | пометка в заголовок, если кого-то подтянули |
| `_flat_nodes(ctx)` | список регионов для круговой и плиток |
| `_tree_nodes(ctx)` | узлы для лучей и сосулек: области **и** макрорегионы |
| `_hierarchy_style(fig)` | размер шрифта подписей, общий для всех четырёх |

**Почему эти четыре вида собираются через `graph_objects`, а не `plotly.express`.**
У макрорегиона нет своей строки в данных — `px` считает его суммой детей,
и подставить ему настоящее значение в подпись невозможно, выходило
«Юго-восток(?)». Поэтому список узлов строится вручную в `_tree_nodes`,
и у каждого узла есть и подтянутый размер, и настоящее число.

**Побочное следствие.** Размер макрорегиона обязан равняться сумме размеров
детей, иначе plotly отвергает `branchvalues="total"`. Поэтому «Центр» нарисован
как сумма подтянутых (158 911), а подписан настоящей суммой (133 081).

#### Карта — нарисована вручную, и это вынужденно

`px.choropleth` **не заработал**. Ни штатный `fitbounds="locations"`, ни ручной
`projection.scale` не масштабировали страну: Казахстан оставался пятном в несколько
пикселей посреди пустого поля.

Доказать это было непросто — разметка врала, потому что в путях SVG лежит и настоящая
геометрия, и прямоугольник обрезки. Помогла растеризация: отрендерили график в картинку
и посчитали пиксели.

```
через px.choropleth :   4 647 закрашенных пикселей  ← это подпись, карты нет
контурами вручную   : 149 913, из них 148 173 синих ← карта
```

Поэтому области рисуются обычными закрашенными контурами (`go.Scatter` с `fill="toself"`)
на простых осях. Координаты кладутся как есть, никакой проекции.

Одна поправка обязательна: **градус долготы короче градуса широты**, и тем сильнее, чем
севернее. Без неё страна выглядит растянутой вширь. Отсюда `scaleanchor="x"` и
`scaleratio = 1/cos(широты)` — для Казахстана вышло 1.45.

Шкала цвета сбоку сделана невидимой точкой с `colorbar` — приём странный, но это
стандартный способ получить шкалу при ручной отрисовке.

`_rings()` разворачивает контуры в один список точек, разделяя части `None`: иначе конец
одного острова соединился бы прямой с началом следующего.

**Чем это хуже настоящей карты.** Это не картографическая проекция. Для одной страны
на средних широтах разница незаметна, но для измерения площадей и расстояний такой
график не годится — он отвечает только на вопрос «где больше, где меньше».

Сопоставление названий областей с файлом границ — в `config.yaml` → `geo.region_map`.
Если область не найдётся, карта покажет **список ненайденных** вместо графика:
молча незакрашенный регион никто бы не заметил.

#### Когда данных за год нет

Источники разной длины: у одних показателей есть 2022–2026, у других только два года.
Пользователь может выбрать сочетание, которого нет.

Раньше на этом падали четыре вида. Теперь все возвращают `_message(NO_DATA)` —
понятную надпись вместо ошибки.

#### Виды, которые ведут себя не как остальные

Это намеренно:

| Вид | Особенность |
|---|---|
| «Сравнение лет», «Наклон» | берут все годы сразу — фильтр года на них не влияет |
| «Точки», «Параллельные оси» | берут все показатели сразу — фильтр показателя не влияет |
| «Динамика по месяцам» | единственный, кто не сворачивает год (этап 4) |
| «Карта» | если область не нашлась в файле границ — показывает список вместо графика |

В `plotly.express` встроено **39 функций-графиков**, в `plotly.graph_objects` — **49**
типов трейсов. Ставить дополнительные библиотеки для диаграмм не нужно.

## Этап 2 — реальные данные и ETL

Что появилось: подключение к PostgreSQL, разведка базы, загрузчик 50 таблиц
и прогон ETL с хранилищем DuckDB, инкрементальностью, сверкой и логом.

### `core/db.py` — подключение к базе

Строка подключения живёт в **`.env`**, а не в коде: файл в `.gitignore`, поэтому
пароль не попадёт в git даже случайно.

```
DATABASE_URL=postgresql+psycopg2://postgres@localhost:5432/test_ai
```

Пароля в этой строке нет, потому что локальная база настроена на trust-аутентификацию.
У боевой он появится — и именно ради этого случая файл вынесен из git.

| Функция | Что делает |
|---|---|
| `get_engine()` | движок SQLAlchemy, кэшируется — пул соединений должен быть один на процесс |
| `check_connection()` | проверка живости, возвращает версию СУБД |
| `list_tables()` | перечень таблиц с колонками — для разведки незнакомой базы |
| `count_rows(table)` | число строк; вынесено отдельно, потому что на больших таблицах `COUNT(*)` не бесплатен |
| `read_sql(query)` | выполнить запрос, вернуть таблицу |

`pool_pre_ping=True` в движке спасает от «протухших» соединений: пул мог держать
соединение, которое сервер уже закрыл по таймауту.

Драйвер — `psycopg2-binary`, он в `requirements.txt`. Для другой СУБД меняется
драйвер и начало строки подключения, остальной код не трогается.

### `etl/explore.py` — разведка базы

```bash
python -m etl.explore
```

Ничего не меняет, только читает. Первое, что стоит запустить, получив доступ
к незнакомой базе: печатает версию СУБД, список таблиц с объёмами и ищет колонки
вида `updated_at` — признак изменений для инкрементального ETL.

На базе `test_ai` таких колонок не нашлось, и это записано в дорожную карту вместе
с найденной заменой (служебная статистика PostgreSQL — см. `etl/run.py` ниже).

### `etl/load_budget.py` — данные из БД в таблицу фактов

```bash
python -m etl.load_budget
```

Источник — 50 таблиц `budget_regions_ММ.ГГ`, по одной на месяц. Структура у всех
одинаковая, поэтому склеиваются одним `UNION ALL` и разворачиваются в длинную форму
**на стороне БД**: наружу едут готовые факты, а не сырые широкие таблицы.

Две вещи, ради которых стоит заглядывать в этот файл:

**`INDICATORS`** — соответствие «колонка в БД → код показателя и тип величины».
`flow` суммируется за год, `stock` берётся на последнюю дату. Тип нужен потому,
что данные помесячные, а показываем мы годовые.

**`REGION_MAP`** — соответствие названий областей. В базе «Абайская область»
и «Область Жетысу», у нас «Абай» и «Жетісу» с казахской `і`. Совпадали только три
города из двадцати. Написано явным словарём, а не подбором по похожести.

Если в базе появится регион, которого нет в `REGION_MAP`, **загрузчик откажется
работать** и назовёт его. Иначе область молча выпала бы из всех отчётов.

`month_tables()` читает список таблиц из базы, а не хранит его в коде: появится
новый месяц — подхватится сам.

Запуск руками (`python -m etl.load_budget`) пишет CSV — сайту он с этапа 3
не нужен, но удобен, чтобы посмотреть данные глазами. Боевой путь другой:
`etl/run.py` зовёт `load_budget.load()` напрямую и пишет в DuckDB.

### `etl/run.py` — прогон ETL: БД → DuckDB

```bash
python -m etl.run           # обычный прогон
python -m etl.run --force   # пересчитать, даже если источник не менялся
```

Этот скрипт на этапе 5 будет дёргать cron каждые 5 минут, поэтому главное
требование к нему — **дешёвый холостой ход**. Порядок работы:

```
отпечаток источника ──совпал с прошлым──▶ выход за секунды
        │
   не совпал
        ▼
 load_budget.load() ──▶ BEGIN ──▶ facts ──▶ сверка ──▶ versions ──▶ COMMIT
                                              │
                                        не сошлась ──▶ ROLLBACK, ошибка
```

#### Отпечаток источника — как ловим изменения без `updated_at`

Колонок вида `updated_at` в базе нет (это выяснила разведка `etl/explore.py`).
Вместо них — служебная статистика PostgreSQL `pg_stat_user_tables`:
накопительные счётчики вставок, изменений и удалений по каждой таблице.
Один дешёвый запрос сворачивает их в строку-отпечаток:

```
50 таблиц / 1000 строк / 1000 изменений
```

Любая правка данных сдвигает счётчик — отпечаток меняется. Отпечаток хранится
в таблице `versions`; при следующем прогоне сравнивается с новым. Если админы
сбросят статистику сервера, отпечаток собьётся и мы пересчитаем лишний раз —
ошибка идёт в безвредную сторону: **пропустить изменения нельзя**.

#### Таблицы в `data/analytics.duckdb`

- **`facts`** — та же общая таблица фактов, колонка в колонку.
  Перезаписывается целиком при каждом пересчёте
- **`versions`** — журнал загрузок: номер версии, время, отпечаток источника,
  число строк, длительность. Последняя строка = текущее состояние хранилища.
  С этапа 3 на номере версии держатся кэш и автообновление страницы

#### Сверка — почему другим запросом

После записи суммы по каждому показателю считаются в PostgreSQL **заново,
но другим запросом**: напрямую по исходным широким колонкам, без разворота
в длинную форму. Если разборщик где-то потерял или задвоил строки, суммы
разойдутся. Сверять тем же запросом, каким грузили, бессмысленно — он
согласится сам с собой вместе со своей ошибкой.

#### Транзакция — почему запись и версия неразделимы

`facts` и строка в `versions` пишутся одной транзакцией. Не сошлась сверка,
оборвалась запись — `ROLLBACK` возвращает прошлое состояние целиком. Момента
«данные уже затёрты, а версии ещё нет» не существует. Это тот же принцип,
что у `parse_msp`: лучше остаться со старыми данными, чем записать кривые.

#### Лог `data/etl.log`

Каждый прогон — и холостой, и полный — пишется в файл и в консоль:

```
2026-07-23 14:19:51  INFO     пересчёт: первая загрузка
2026-07-23 14:19:51  INFO     версия 1: 7 000 строк, сверка по 7 показателям сошлась, 0.2 сек
2026-07-23 14:19:52  INFO     источник не менялся (50 таблиц / 1000 строк / 1000 изменений) — пересчёт пропущен, 0.1 сек
```

Файл нужен ради cron: по расписанию консоль никто не увидит, и при падении
лог — единственный свидетель (ошибки пишутся с полным следом).

#### Функции

| Функция | Что делает |
|---|---|
| `setup_logging()` | лог в файл и консоль одновременно |
| `ensure_schema(con)` | создаёт таблицу `versions`, если её ещё нет |
| `source_fingerprint()` | отпечаток источника из `pg_stat_user_tables` |
| `last_fingerprint(con)` | отпечаток последней загрузки из `versions` |
| `verify(con, tables)` | сверка контрольных сумм; возвращает список расхождений |
| `run(force)` | весь цикл: проверка → загрузка → сверка → версия |
| `main()` | разбор `--force`, перехват ошибок в лог |

## Этап 3 — соединение и «живость»

Что появилось: сайт читает DuckDB вместо CSV, кэш с ключом-версией данных,
автообновление открытой страницы без F5.

### `core/cache.py` — общий кэш

Кэш flask-caching, хранение в памяти процесса (`SimpleCache`). Кэшируемые функции
помечаются декоратором `@cache.memoize()`: результат запоминается **по аргументам**,
поэтому аргумент функции — это и есть ключ кэша. На этом строится вся свежесть:
у конфига в аргументе время правки файла, у фактов — номер версии данных.

Две привязки, обе нужны:

- к запасному Flask-приложению прямо в модуле — чтобы кэш работал из
  python-консоли и тестов, без сайта;
- к настоящему приложению сайта в `app.py` (`cache.init_app(server)`).

!! **Главные грабли:** без второй привязки flask-caching внутри веб-запроса
не находит кэш и **молча работает без него** — сайт выглядит здоровым, только
медленным. Симптом ищется в логе сервера по строкам
«Exception possibly due to cache backend».

Почему flask-caching, а не `lru_cache` из стандартной библиотеки: на этапе 5
сайт пойдёт под Gunicorn в несколько процессов-воркеров, и там достаточно
сменить `CACHE_TYPE` на общее хранилище (файлы, Redis), чтобы воркеры делили
один кэш. `lru_cache` такого пути не даёт.

Результат в цифрах: построение «полос» 233 → 43 мс, повторный выбор фильтра
~0.4 сек вместо ~1 сек.

### `core/data.py` — чтение хранилища и кэш

#### `_query_storage(query) -> pd.DataFrame`

Единственное место, открывающее DuckDB-файл. Две задачи:

- **понятная ошибка**, если хранилища нет: «Сначала запустите python -m etl.run»
- **повтор при занятом файле**: пока `etl.run` переписывает хранилище (доли
  секунды раз в несколько минут), файл заперт на запись. Попав в это окно,
  функция не падает, а пробует ещё несколько раз с паузой

#### `get_data_version() -> int`

Номер последней загрузки ETL — одна строка из таблицы `versions`, дёшево.
На нём держится вся «живость» сайта: номер входит в ключ кэша фактов, а открытая
страница раз в 30 сек сверяет его со своим. Намеренно **не** кэшируется —
это и есть проба свежести.

#### `load_facts() -> pd.DataFrame`

Читает таблицу `facts` из `data/analytics.duckdb`.

> **Это единственное место во всём проекте, которое знает формат источника.**
> До этапа 3 здесь читались CSV-файлы — временная затычка на период без БД.
> Переезд на DuckDB поменял только тело этой функции: она вернула DataFrame
> с теми же колонками, и страницы, диаграммы, реестр показателей не заметили
> смены источника. Ради этого «узкая талия» и строилась.

**Кэшируется по версии данных** — и это разрешает старый конфликт «быстро или
свежо». Пока ETL не записал новую версию, повторные вызовы получают копию из
памяти. Записал — `get_data_version()` вернёт новый номер, ключ кэша сменится,
факты перечитаются. Кэш не «протухает по таймеру», а привязан к данным.

Строка `df["is_total"] = df["is_total"].astype(bool)` осталась с CSV-времён —
DuckDB типы хранит, так что теперь это просто страховка.

#### `load_config() -> dict`

Читает `config.yaml` целиком — через кэш. За одну отрисовку конфиг нужен десятки
раз, и до кэша каждое обращение перечитывало диск: на это уходила большая часть
времени отклика. Ключ кэша — время правки файла (`mtime`): поправили конфиг —
ключ сменился, свежие настройки подхватились сами, без перезапуска.

#### `get_last_update() -> str`

Когда хранилище обновлялось в последний раз — «ЧЧ:ММ» из таблицы `versions`.
Показывается под заголовком страницы («данные обновлены в 14:49») и
перерисовывается автообновлением вместе с остальным.

### `pages/main.py` — автообновление без F5

В layout, кроме видимых элементов, лежит невидимая пара, на которой держится
автообновление: `dcc.Interval(id="data-poll")` — таймер, тикающий раз в 30 сек,
и `dcc.Store(id="data-version")` — запомненный страницей номер версии данных.

#### `poll_version(...)` — коллбэк-сторож

```python
@callback(
    Output("data-version", "data"),
    Output("data-updated", "children"),
    Input("data-poll", "n_intervals"),
    State("data-version", "data"),
)
```

Каждый тик таймера сверяет версию хранилища с той, что помнит страница:

- **совпала** — вернуть `no_update`: ничего не перерисовывается, холостая
  проверка стоит одну строку из DuckDB
- **выросла** — записать новый номер в Store и обновить подпись
  «данные обновлены в ЧЧ:ММ»

У коллбэков карточек, графика и таблицы среди входов есть
`Input("data-version", "data")` — смена номера в Store перерисовывает их
с **текущими** значениями фильтров.

!! **Фильтры при этом не сбрасываются** — и вот почему. Сбрасывала их горячая
перезагрузка: она перезагружала страницу целиком, как F5, и браузер строил всё
заново. Interval страницу не перезагружает — он лишь дёргает коллбэки, а те
меняют только свои выходы. Состояние фильтров живёт в браузере и переживает
любое число таких перерисовок. Проверено вживую: выставили 2025/«Освоено»,
прогнали ETL, дождались обновления — выбор на месте.

Разница `Input` и `State` в этом коллбэке — учебная: `Input` запускает коллбэк
при своём изменении, `State` только подставляет текущее значение, не запуская.
Таймер — `Input` (он и будит), запомненная версия — `State` (её меняем мы сами).

На этапе 4 на эту же цепочку надет «шлагбаум» отложенной публикации:
ETL пишет версии со статусом «ждёт публикации», в 9:00 они становятся
опубликованными — и в течение минуты у всех открытых страниц цифры меняются.
Как это устроено — в разделе этапа 4 про `core/publish.py`.

## Этап 4 — ручной ввод и кастомизация (ввод и публикация готовы)

Сделано: производная карточка, месячная динамика, видимые галки (первая волна) +
таблица `plan`, форма ввода, отложенная публикация с вето и плашкой админа
(вторая волна, 23.07.2026). Осталось: тема (`core/theme.py`), страница настроек
и CSS-переменные со шрифтом — их разделы появятся здесь по мере готовности.

### Производная карточка «Согласно плану %»

Карточки бывают двух сортов. Обычные берут итог показателя из данных.
**Производные** в данных не лежат — считаются из итогов двух других
показателей. В конфиге у такого показателя есть блок `derived`:

```yaml
budget_execution:            # «Согласно плану %»
  derived:
    numerator: budget_spent        # факт — освоено
    denominator: budget_allocated  # план — выделено
```

Расчёт — в `get_kpi` (`core/data.py`): сначала итоги по стране каждого
показателя по своему правилу, потом деление. Готовую колонку
`execution_percent` из БД не берём осознанно: производное надо считать
из частей, иначе однажды разойдётся с ними.

Изменение к прошлому году у производной карточки — в **процентных пунктах**
(рост с 78 % до 80 % — это +2 п.п., а не «+2.6 %»). В строке это поле
`change_kind`: `pct` — обычные проценты, `pp` — пункты; подпись выбирает
`kpi_card` в `pages/main.py`.

?? **Открытый вопрос заказчику:** сейчас процент — от плана за прошедшие месяцы
(обе суммы за загруженные месяцы года). Если нужно «от годового плана» —
менять расчёт в `get_kpi`.

### `assets/custom.css` — свои стили

Dash подхватывает всё из `assets/` сам, подключать в коде не нужно. Правки

### `core/publish.py` — отложенная публикация

Правило одно на всё: **то, что появилось в момент T, публикуется в ближайшие
9:00 строго после T**. Правка в 16:00 вторника выходит в среду утром; правка
в 8:00 — через час. До своих 9:00 правку можно отменить.

Решения, принятые 23.07.2026 (разбор вариантов — в ROADMAP): публикация каждый
день, включая выходные; время — по часам сервера; после простоя сервера
публикуется всё дозревшее при первом же запуске; вето снимает админ вручную
(@@ решили вернуться — возможно, переделаем); уведомление — плашка на сайте,
видна только админу.

Под правилом живут две разные вещи:

- **план** — строки таблицы `plan` со статусом `draft`. В 9:00 черновик
  становится `published` и только с этого момента виден витрине. Отмена —
  удаление строки-черновика; повторная правка того же поля заменяет черновик,
  а не копит строки
- **версии данных из БД** — каждый прогон `etl.run` со свежими данными кладёт
  снимок фактов под новым номером со статусом `pending`. В 9:00 публикуется
  самая свежая незабракованная; сайт до тех пор показывает прежнюю

Статусы — английские коды в данных (`draft/published`,
`pending/published/rejected/superseded`), русские подписи для экрана —
в словаре `STATUS_LABELS`, интерфейс их не выдумывает.

#### Как устроено время: `next_publish_time` и `last_deadline`

Две функции-зеркала. `next_publish_time(T)` — ближайшие 9:00 строго после T:
когда правка выйдет (для подписей «опубликуется завтра в 09:00»).
`last_deadline(now)` — последний рубеж 9:00, который уже наступил: правка
дозрела ⇔ её штамп раньше этого рубежа. Второе выражение — одно неравенство,
и оно уходит прямо в SQL-запросы публикации.

#### `publish_due(now=None)` — сам шлюз

Не «срабатывает в 9:00», а отвечает на вопрос «что уже дозрело?» — поэтому
неважно, лежал ли сервер в 9:00: первая же проверка после подъёма публикует
пропущенное. Никакого отдельного планировщика нет: шлюз дёргают 30-секундный
опрос каждой открытой страницы и каждый прогон `etl.run`. В холостую это два
маленьких чтения.

Внутри одной транзакции: самая свежая дозревшая `pending`-версия становится
`published` (прежняя — `superseded`, обогнанные — тоже), дозревшие черновики
плана замещают опубликованные строки с тем же ключом. Снимки фактов заменённых
версий чистятся, последние `KEEP_SNAPSHOTS` (3) остаются на откат; журнал
в `versions` не трогается — он помнит всё.

Параметр `now` нужен для проверок: подставив «завтра 9:01», публикацию можно
прогнать не дожидаясь настоящего утра (см. «Как запускать»).

#### Вето

`reject_version(v)` — pending-версия помечается забракованной и в 9:00
не выйдет; сайт продолжает показывать прежнюю. Исправлять надо источник:
следующая версия из БД пройдёт штатно. `restore_version(v)` — версия снова
pending; если срок уже прошёл, ближайшая проверка опубликует её в течение
полминуты — снятие вето это, по сути, немедленная публикация.

#### `migrate()` — хозяин схемы

Схема `versions` и `plan` описана здесь, а не в `etl/run.py`: и ETL, и сайт
зовут один код. Миграция идемпотентна: старому хранилищу добавляются колонки
`status`/`published_at`/`version`, последняя версия объявляется опубликованной.
Зовётся при старте сайта (`app.py`) и в начале каждого прогона ETL.

#### !! Два граблей DuckDB, на которые уже наступили

- **Чтение и запись не смешиваются в одном процессе.** Пока один поток сайта
  держит соединение на запись (публикация, сохранение черновика), чтение
  в соседнем потоке получает `ConnectionException`. Лечится ожиданием — повторы
  уже встроены и в `_query_storage` (core/data.py), и в `_connect_write`
- **`publish_due` всегда открывает своё соединение.** Вариант «работать на чужом
  соединении etl.run» ловил внутреннюю ошибку DuckDB 1.5.4 (`Attempted to access
  index 0 within vector of size 0`) сразу после большой вставки на том же
  соединении. Поэтому `etl.run` сначала закрывает своё соединение — потом зовёт
  публикацию

### `core/auth.py` — кто вошёл (пока заглушка)

`current_user()` — имя пользователя ОС (в черновиках плана видно, кто писал),
`current_role()` — всегда `admin` до этапа 5, `is_admin()`. Смысл файла не в
заглушке, а в правиле: **всё, что видно только админу, спрашивает роль здесь** —
плашка публикации, ссылка и страница «Ввод плана». На этапе 5 LDAP заменит
тело этих функций, страницы не тронутся.

### `pages/plan_input.py` — форма ввода плана

Три раздела: форма (показатель + год + значение → черновик с автором
и временем), «Черновик» с кнопками отмены, версии данных из БД с кнопками
«Забраковать»/«Снять вето». Вся механика — в `core/publish.py`, страница
только показывает состояние и передаёт нажатия.

`plan_indicators()` — показатели для формы собираются из реестра: те, что
названы `denominator` в блоках `derived` конфига. Не перечислены словами
намеренно (то же правило, что у галки логарифма): появится новая производная
карточка — её знаменатель попадёт в форму сам.

Проверка ввода: значение — число ≥ 0, год в разумных пределах; при ошибке
красная плашка, в хранилище ничего не пишется.

Кнопки в таблицах — с **pattern-matching id** (`{"type": "plan-cancel",
"index": ...}`): их число заранее неизвестно, и один коллбэк `handle_actions`
слушает их все через `ALL`, разбирая `ctx.triggered_id`. Он же — единственный
коллбэк страницы: любое действие в конце перерисовывает все три списка.

### Изменения этапа 4 в старых файлах

**`core/data.py`.** `get_data_version()` превратилась в пару:
`get_published_version()` — номер опубликованной версии, ключ кэша фактов;
`get_display_version()` — строка «версия фактов + отпечаток плана» для
автообновления: публикация плана не меняет номер версии фактов, но экран
перерисовать должна. `load_facts()` читает только опубликованный снимок
(`WHERE version = ...`, служебная колонка наружу не отдаётся — форма данных
для страниц не изменилась). `get_published_plan(year)` — опубликованный ручной
план; в `get_kpi` он подменяет **знаменатель** производных карточек: есть
ручной план — «Согласно плану %» считается от него (годового), нет — от фактов,
как раньше. `get_last_update()` показывает момент публикации, а не разбора.

**`etl/run.py`.** Снимки фактов копятся под номерами версий, а не затирают
друг друга; новая загрузка — `pending` (первая в жизни хранилища — сразу
`published`, ей нечего ждать). Сверка — только по новому снимку
(`WHERE version = ?`). Схему ведёт `publish.migrate(con)`. Соединение
закрывается явно, публикация зовётся после закрытия.

**`pages/main.py`.** В `poll_version` перед сверкой версии дёргается
`publish.publish_due()` — так публикация и происходит: ровно в первый опрос
после 9:00. Плашка `publish_banner()` («ждёт публикации: версия N, черновиков
плана: M») собирается каждый опрос и видна только админу.

**`app.py`.** `app.layout` стал функцией `serve_layout` — меню собирается
на каждый запрос, зрителю ссылка «Ввод плана» не показывается.
При старте — `publish.migrate()` и `logging.basicConfig(INFO)`: без него
строки «опубликовано: версия данных N» из страниц молча пропадали бы
(уровень Python по умолчанию — WARNING).

### Что сломается, если

**Удалить `data/analytics.duckdb`** → страница покажет жёлтую плашку с подсказкой
запустить `python -m etl.run`. Приложение не упадёт. Факты восстанавливаются
этой одной командой — правда, история версий начнётся заново.
!! **А вот ручной план — нет:** таблица `plan` наполняется через форму,
в боевой БД её данных не существует. С этапа 4 удаление хранилища теряет план
безвозвратно. Бэкап — задача этапа 5.

**Забраковать все ожидающие версии** → сайт спокойно живёт на последней
опубликованной. Публиковать станет нечего, пока источник не изменится
(придёт новая версия) или админ не снимет вето с одной из забракованных.

**Сервер лежал в 9:00** → ничего не пропадает: первый же опрос страницы или
прогон ETL после подъёма публикует всё дозревшее (решение от 23.07.2026).

**Заменить Excel на выгрузку за другой квартал** → разборщик отработает, но проставит
**старые даты и годы из `SPEC`**. Их нужно поправить вручную. Это осознанное решение:
лучше править одну таблицу, чем угадывать период по кривой шапке и однажды угадать неверно.

**У источника съедет шапка** → сверка сумм с итогом развалится, разборщик откажется
записывать файл и напечатает, где именно разошлось.

**В БД появится новый регион** → `load_budget` откажется работать и назовёт его,
пока соответствие не добавят в `REGION_MAP`. Иначе область молча выпала бы из отчётов.

**Опечататься в коде показателя в `config.yaml`** → ошибки не будет, но поведение
двойственное, и это стоит знать (проверено на живом коде):

- **карточка не появится** — `get_kpi` пропускает показатели, которых нет в данных
- **в выпадающем списке фильтра его не будет** — список показывает только то,
  по чему есть данные
- если код показателя опечатан в `kpi_order` — колонка просто выпадет из таблицы

Пустой экран без объяснений — самый неприятный вид поломки: непонятно, то ли данных
нет, то ли опечатка. Поэтому сверяйте написание кода показателя с `INDICATORS`
в загрузчике (или `SPEC` в разборщике).
